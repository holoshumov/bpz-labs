# ЛР5 — нотатки

## Теорія коротко
- **JWS** (RFC 7515) = `base64url(header).base64url(payload).base64url(signature)`. **RS256** — RSA-PKCS#1 v1.5 + SHA-256: Auth0 підписує приватним ключем, сервер перевіряє публічним із JWKS (`/.well-known/jwks.json`, ключ за `kid`) або `/pem`.
- Перевіряти треба не лише підпис, а й `iss`, `aud`, `exp` (`nbf`), і фіксувати допустимі `alg` (атаки `alg=none`, підміна RS256→HS256).
- **JWE** (RFC 7516) — 5 частин: header, зашифрований CEK, IV, ciphertext, tag. `RSA-OAEP-256` шифрує випадковий ключ вмісту (CEK), `A256GCM` шифрує payload і дає тег автентичності.
- JWS дає цілісність і автентичність, але не конфіденційність; JWE — конфіденційність.

## Що зроблено (`evidence/demo-own.log`, `evidence/demo-kpi.log` — однакові результати на обох tenant'ах)
| Сценарій | Результат |
|---|---|
| Валідний JWE | 200 |
| Payload JWE без ключа | шифротекст, `JSON.parse` — помилка; чужий приватний ключ — `decryption operation failed` |
| Пошкоджений JWE | 401 `ERR_JWE_DECRYPTION_FAILED` |
| Оригінальний Auth0 JWS | 200 |
| Підмінений payload (sub/scope) | 401 `signature verification failed` |
| Токен, підписаний чужим RSA-ключем (той самий kid/iss/aud) | 401 `signature verification failed` |
| `alg=none` | 401 `ERR_JOSE_ALG_NOT_ALLOWED` |
| Справжній токен на момент `exp+1` | `ERR_JWT_EXPIRED` (claim `exp`) |
| Чужа `aud` | `ERR_JWT_CLAIM_VALIDATION_FAILED` (claim `aud`) |

## Питання до захисту
1. **Звідки сервер бере публічний ключ?** — JWKS `https://<domain>/.well-known/jwks.json` (кешується, ключ вибирається за `kid`); альтернатива — `https://<domain>/pem`.
2. **Що саме підписано?** — Рядок `header.payload` (base64url) — тому будь-яка зміна payload ламає підпис.
3. **Чому не досить перевірити підпис?** — Валідний токен може бути для іншого API (`aud`), від іншого issuer або простроченим.
4. **Що таке атака alg=none?** — Токен без підпису з `alg: none`; захист — allow-list алгоритмів (`algorithms: ['RS256']`).
5. **RS256 vs HS256?** — RS256 асиметричний (перевіряє будь-хто з публічним ключем, підписує лише Auth0); HS256 — спільний секрет, який мав би знати кожен перевіряльник.
6. **Чи можна прочитати JWE на jwt.io?** — Ні: payload зашифровано AES-256-GCM, ключ CEK зашифровано RSA-OAEP публічним ключем сервера; розшифрувати може лише власник приватного ключа.
7. **Навіщо всередині JWE ще й підписаний токен?** — JWE дає конфіденційність, а підпис Auth0 — доказ, що дані видав Auth0; сервер після розшифрування перевіряє і його.
8. **Що таке tag у A256GCM?** — Тег автентичності GCM: будь-яка зміна шифротексту/IV/header → розшифрування не вдається (у нас — пошкоджений JWE → 401).
9. **Що буде при ротації ключів Auth0?** — Новий `kid`; `createRemoteJWKSet` перезавантажить JWKS при невідомому `kid`.
10. **Де зберігається ключ JWE?** — `lab5/keys/jwe-private.pem` (права 600, у `.gitignore`); у проді — KMS/секрет-сховище.
