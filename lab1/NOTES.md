## Як запустити
```bash
npm install
npm run basic   # або forms | token | jwt — усі на :3000, запускати по одному
./requests.sh basic   # у другому терміналі: curl-сценарій для відповідного застосунку
JWT_SECRET=інший npm run jwt   # JWT з іншим секретом
```
Облікові дані: basic — `DateArt` / `2408`; forms/token/jwt — `Login` / `Password` (або `Login1` / `Password1`).

### Відомий баг оригіналу (`forms_auth`, `token_auth`)
У `POST /api/login` після `res.json(...)` немає `return`, тому виконується ще й `res.status(401).send()`.
Що реально відбувається на Node 24 + Express 4.22 (перевірено окремим тестом): **помилки `ERR_HTTP_HEADERS_SENT` у консолі немає** — `res.send()` з порожнім тілом не виставляє заголовків, а повторний `end()` по вже завершеній відповіді Node мовчки ігнорує. Клієнт отримує `200` і JSON, але `res.statusCode` на сервері після цього = 401 (тобто логи/middleware, що дивляться статус після відповіді, побачили б 401). Якби там було `res.status(401).send('Unauthorized')` (з тілом) — Express спробував би поставити `Content-Type` і впав би з `ERR_HTTP_HEADERS_SENT`. Правильне виправлення — `return res.json(...)` (так зроблено в `token_auth_jwt`). Оригінали за умовою не виправлялись.

## 1. Як працює кожен метод

### Basic Authentication (`basic_auth`)
- **Потік:** запит без `Authorization` → `401` + `WWW-Authenticate: Basic realm="Ukraine"` → браузер показує нативне вікно → далі в **кожному** запиті `Authorization: Basic base64(login:password)`.
- **Хто зберігає стан:** ніхто — сервер щоразу перевіряє логін/пароль, браузер кешує їх до закриття вікна.
- **Що передається щоразу:** сам пароль (base64 — це кодування, не шифрування: `RGF0ZUFydDoyNDA4` → `DateArt:2408`).
- **Слабкі місця:** без HTTPS пароль читається будь-ким у мережі; пароль летить у кожному запиті (більше шансів витоку, в т.ч. у логах — сервер прямо логує його); немає нормального logout; немає захисту від перебору; сервер порівнює пароль у відкритому вигляді (`==`, не хеш, не constant-time); `split(':')[1]` обрізає пароль, якщо в ньому є `:`.

### Forms (session cookie) (`forms_auth`)
- **Потік:** перший `GET /` → сервер генерує `uuid` сесії і ставить `Set-Cookie: session=<uuid>; HttpOnly`; `POST /api/login` (JSON з логіном/паролем) → сервер записує `username` у сесію; надалі браузер **автоматично** шле `Cookie: session=<uuid>`.
- **Хто зберігає стан:** сервер (`sessions.json` — сесії переживають рестарт; у реальних системах — Redis/БД). Клієнт має лише ідентифікатор.
- **Що передається:** тільки session id у cookie.
- **Слабкі місця:** session id = ключ до акаунта (крадіжка cookie → викрадення сесії); немає `Secure` і `SameSite` → вразливість до CSRF і передача по HTTP; немає терміну дії сесії; id сесії не змінюється після логіну (**session fixation**); `sessions.json` — синхронний запис на кожен запит, не масштабується на кілька серверів, файл містить дані всіх сесій; logout лише очищує cookie (не ставить `Max-Age=0`); паролі у відкритому вигляді в коді.

### Token (uuid) (`token_auth`)
- **Потік:** `POST /api/login` → `{"token":"<uuid>"}`; клієнт кладе його в `sessionStorage` і шле вручну в заголовку `Authorization: <uuid>` (без схеми `Bearer`).
- **Хто зберігає стан:** і сервер (`sessions.json`: uuid → користувач), і клієнт (sessionStorage). Це той самий session id, лише переданий заголовком, а не cookie.
- **Плюси vs cookie:** браузер не шле заголовок автоматично → немає CSRF; зручно для API/мобільних клієнтів.
- **Слабкі місця:** токен у JS-доступному сховищі → викрадається при XSS; токен без терміну дії (вічний, доки є запис у файлі); сервер створює новий запис сесії на **кожен** запит без токена (файл росте → легко DoS); logout на сервері не працює (посилання `/logout` іде без заголовка), клієнт лише видаляє токен з sessionStorage; той самий баг без `return`.

### JWT (`token_auth_jwt`) — додаткове завдання
- **Потік:** `POST /api/login` → сервер підписує `{sub, username, iat, exp}` і віддає `{"token":"<header>.<payload>.<signature>"}`; клієнт шле `Authorization: Bearer <jwt>`; сервер перевіряє підпис і `exp` — без жодного сховища.
- **Хто зберігає стан:** лише клієнт (токен). Сервер **stateless**, знає тільки секрет.
- **Слабкі місця:** токен не можна відкликати до `exp` (без додаткового blacklist); payload читає будь-хто (base64url); секрет за замовчуванням зашитий у код (`change-me-lab1-secret`) — у продакшені тільки зі змінної оточення / secret manager; токен у sessionStorage → XSS.

## 2. Що змінено для JWT і чому
| Зміна | Навіщо |
|---|---|
| `jwt.js`: власна реалізація HS256 на вбудованому `crypto` (без бібліотек) | Видно всю «механіку»: `base64url(header).base64url(payload).base64url(HMAC-SHA256(header.payload, secret))`. |
| Прибрано `sessions.json` і клас `Session` | **Stateless**: усе потрібне в самому токені, сервери можна масштабувати горизонтально, достатньо спільного секрету. |
| Підпис **HMAC-SHA256** з `JWT_SECRET` (з env) | Цілісність і автентичність: змінити payload (напр. `username: admin`) без секрету неможливо → `401 Invalid signature`. Зміна секрету інвалідує всі старі токени (перевірено). |
| `iat` + `exp` (TTL 1 год) | На відміну від uuid-токена, JWT має термін дії; прострочений → `Token expired`. |
| `Authorization: Bearer <jwt>` | Стандартна схема RFC 6750 замість «голого» токена. |
| Перевірка `header.alg === 'HS256'` | Захист від атаки **`alg: none`** (і від підміни алгоритму): сервер сам вирішує, яким алгоритмом перевіряти, а не довіряє заголовку токена. |
| `crypto.timingSafeEqual` для порівняння підпису (+ перевірка довжини) | Захист від **timing-атаки**: звичайне `===` завершується на першому різному байті, і за часом відповіді можна підбирати підпис побайтово. |
| `return res.status(401)` / `return res.json` | Виправлено баг подвійної відповіді з оригіналу. |
| `index.html`: `Bearer`, показ токена і розкодованого payload | Для демонстрації на скріншотах/захисті. |
| Logout = клієнт видаляє токен | Серверу нічого видаляти — stateless. |

## 3. Ймовірні питання на захисті

1. **Чим відрізняється автентифікація від авторизації?** Автентифікація — перевірка, хто ти (логін/пароль, токен). Авторизація — що тобі дозволено (ролі, права). У лабі реалізована лише автентифікація.
2. **Чому Basic Auth небезпечний без HTTPS?** Base64 — оборотне кодування, не шифрування. Пароль у кожному запиті, будь-хто з доступом до трафіку (Wi-Fi, проксі) його розкодує. З HTTPS — прийнятно для простих внутрішніх API, але пароль усе одно частіше «світиться».
3. **JWT vs сесія (cookie)?** Сесія: стан на сервері, клієнт має лише id; легко відкликати (видалити запис), але потрібне спільне сховище при кількох серверах. JWT: стан у токені, сервер stateless, легко масштабувати і використовувати між сервісами, але важко відкликати і токен більший. Сесії — класичні веб-застосунки; JWT — API, мікросервіси, SSO.
4. **Чому payload JWT не секретний? Що туди можна класти?** Він лише base64url-закодований, не зашифрований — будь-хто прочитає (jwt.io). Підпис гарантує **незмінність**, а не конфіденційність. Тому там тільки ідентифікатори/ролі, жодних паролів, персональних даних. Для секретності — JWE (зашифрований JWT).
5. **Як відкликати JWT до закінчення exp?** Короткий `exp` (5–15 хв) + refresh-токен, який зберігається на сервері і відкликається; blacklist/denylist за `jti`; «версія токена» у користувача в БД; зміна секрету (відкликає всі токени одразу — показано в лабі).
6. **HS256 vs RS256?** HS256 — симетричний HMAC: той самий секрет і підписує, і перевіряє (усі сервіси, що перевіряють, можуть і підробляти). RS256 — асиметричний: підписує приватний ключ (лише сервер автентифікації), перевіряє публічний (можна роздати всім, напр. через JWKS). Для кількох сервісів / Auth0 — RS256.
7. **Що таке атака `alg: none` і як ви захистились?** Зловмисник ставить у header `"alg":"none"` і прибирає підпис; наївна бібліотека «перевіряє» токен алгоритмом none і приймає. У нас сервер приймає лише `HS256` → `401 Unsupported alg` (перевірено).
8. **Навіщо `timingSafeEqual`?** Порівняння за сталий час: час відповіді не залежить від того, скільки перших байтів підпису співпало, тож підпис не підібрати побайтово.
9. **Де зберігати токен на клієнті?** `localStorage/sessionStorage` — доступні з JS → викрадення при **XSS**, але немає CSRF. Cookie `HttpOnly; Secure; SameSite=Strict/Lax` — JS не прочитає (захист від XSS-крадіжки), але потрібен захист від **CSRF** (SameSite, CSRF-токен). Компроміс: access-токен у пам'яті, refresh — у HttpOnly cookie.
10. **Що таке CSRF і XSS, хто з методів до чого вразливий?** CSRF — чужий сайт змушує браузер виконати запит, і браузер **автоматично** додає cookie/Basic-креденшели → вразливі forms і basic. Token/JWT у заголовку браузер сам не додає → CSRF не працює, але при XSS (виконання чужого JS на нашій сторінці) токен із sessionStorage можна вкрасти.
11. **Чому в forms cookie `HttpOnly` і чого бракує?** `HttpOnly` забороняє `document.cookie` → XSS не вкраде сесію. Бракує `Secure` (лише HTTPS), `SameSite` (CSRF), `Max-Age`/`Expires`, регенерації id після логіну (session fixation).
12. **Що буде без `return` після `res.json` у login?** Див. «Відомий баг»: друга відповідь мовчки ігнорується, але логіка неправильна, а з тілом — `ERR_HTTP_HEADERS_SENT`.
13. **Чим token_auth відрізняється від forms_auth насправді?** Лише транспортом: той самий серверний session id, але в заголовку `Authorization` замість cookie і в sessionStorage замість cookie-jar. Тому це «opaque token», а JWT — «self-contained token».
